Studio is a local web app for enriching your schema artifact (the files that describe your tables to the model) and testing questions against the SQL they generate. It reads and writes the artifact on your machine. Its AI features send schema text and your questions to the model provider you configure. This tour walks through its seven views.

<Aside type="tip">Studio is the recommended way to enrich your schema: a local browser UI that edits your schema artifact directly. You can also edit the artifact's files by hand, in the [schema artifact format](/reference/schema-artifact-format/).</Aside>

Launch it from your project root:

```bash
npx askdb studio
```

Studio prints its address, `AskDB Studio is running at http://127.0.0.1:5556`. Open that in your browser. Studio reads the schema directory that `introspection.outputDir` in `askdb.config.ts` names. When that isn't set, it reads `./askdb/`. The [Studio reference](/reference/studio/#launch) lists the flags, such as `--schema` and `--port`.

## Guided setup

Studio also works as the *first* command in a new project. Some directories have no `askdb.config.ts`, or no schema artifact yet. In one of those, `npx askdb studio` opens a setup wizard instead:

<Steps>

1. **Pick your database engine and AI provider.** The wizard asks for environment variable *names* only, never secret values. Studio writes `askdb.config.ts` and an `.env.example`, and installs the packages the config needs.
2. **Add your secrets to `.env` yourself.** The wizard shows which variables to fill in. The values stay on your disk.
3. **Run introspection from the browser.** Studio reads your schema's structure (tables and columns, never rows) and opens the Overview.

</Steps>

`npx askdb init` asks the same questions in the terminal and writes the same files. The [Studio reference](/reference/studio/#guided-setup) says what the wizard writes and installs, and how it picks a package manager.

## The loop

The core Studio workflow is **enrich → ask → re-enrich**. Add descriptions, aliases and example questions to a table, then ask a question in the Playground and read the SQL. If it isn't what you expected, tighten the enrichment and ask again, without leaving the browser tab. Repeating this loop is what makes generation reliable for the words your team uses.

## Overview

<figure>

![The Overview dashboard showing table count, enrichment progress, RAG index health, and suggested next actions](../../assets/studio/overview.png)

<figcaption>The Overview: stat cards, pending enrichment, recent Playground queries and suggested next actions.</figcaption>
</figure>

The Overview shows the state of your schema artifact:

- **Stat cards:** tables (with how many are enriched and partly enriched), concepts, the RAG index's health, and sensitivity coverage. The RAG index is the search index that lets AskDB send the model only the part of a large schema that fits the question ([RAG Index](#rag-index)).
- **Pending enrichment:** tables that still need descriptions. Click one to open it in Tables.
- **Recent playground queries,** and cards for the **RAG index** and **Tenancy**.
- **Suggested next actions,** such as describing a table or building the index.

**Resync schema** runs introspection again with the connection in `askdb.config.ts`, as a flag-free `askdb introspect` does. It rebuilds `schema.json` and keeps your enrichment markdown, and any edits you haven't saved yet. A message above the cards says how many tables it read, or why it failed.

## Tables and enrichment

<figure>

![The Tables view showing a table list on the left and the Enrichment tab on the right with description, aliases, and common query language fields](../../assets/studio/tables.png)

<figcaption>The Tables view: the table list, and the open table's Enrichment tab.</figcaption>
</figure>

The Tables view lists every table in your schema, grouped by schema, with a search box and filters for **Complete**, **Partial** and **Not started** tables. A table is **Complete** once it and every one of its columns have a description, and **Partial** once anything is written for it or a column. The Overview counts tables the same way. Select a table to open it in three tabs:

- **Enrichment.** For the table: a description, aliases (the names people use when they ask), a primary entity, tags, common query language and example questions. For each column: a description, aliases and enum notes.
- **Schema.** The columns with their types, nullability, primary key and sensitivity, and the table's relationships.
- **Sensitivity.** First, whether the table is **Tracked**. An untracked table stays in the artifact but out of prompts and the RAG index. Then the table's and columns' sensitivity. A mark can only make something sensitive, so "Not sensitive" is disabled wherever it couldn't take effect. The **Effective** column shows what AskDB uses.

**Save** writes the table's markdown file, and **Revert** drops your unsaved edits.

**Suggest** drafts a value for a field with your model, so you can review a draft instead of writing from scratch. It needs a configured model. It works on these fields:

- A table's description, aliases, primary entity and common query language.
- A column's description and aliases.

The drafts appear under the field, with **Use** on each and **Dismiss** for the set, so you can review several fields at once. **Use** fills the field, and nothing reaches the artifact until **Save**. The [Studio reference](/reference/studio/#ai-features) says what each suggestion sends to the model.

**Suggest all empty fields**, at the top of the Enrichment tab, drafts every empty description and alias of the open table and its columns. It makes one model call per field. It says how many calls it will make, and waits for you to confirm.

`modes.omitSensitiveFromPrompt` is the config setting that leaves sensitive columns out of prompts. With it on, two more rules apply:

- **Sensitive columns are skipped.** Suggest all empty fields says how many it skipped.
- **An unsaved sensitive mark makes Suggest wait.** Suggest sends the saved schema. So while you've marked the table or a column sensitive without saving, every **Suggest** on that table waits for **Save**.

## Concepts

<figure>

![The Concepts view with an empty list and an Add concept button](../../assets/studio/concepts.png)

<figcaption>The Concepts view, before you add a concept.</figcaption>
</figure>

Concepts capture business vocabulary that spans tables, such as "active subscription" or "customer" in a schema where that meaning joins several tables. **Add concept** asks for an ID (Studio adds the `concept:` prefix), a label, synonyms, links to the tables and columns it covers, and a description. **Save** writes `concepts.md`.

Concepts reach the model in both Playground modes: **Full schema** lists every concept, and **RAG** lists the ones retrieval picks (see [RAG Index](#rag-index)). Start with the terms your team reaches for most.

## Tenancy

<figure>

![The Tenancy view offering Draft with AI or Configure manually options for multi-tenant isolation](../../assets/studio/tenancy.png)

<figcaption>The Tenancy view: draft a tenant policy with AI, or configure it manually.</figcaption>
</figure>

The Tenancy view declares tenant isolation for a multi-tenant schema. Start the policy one of two ways:

- **Draft with AI** has your model propose a tenant policy.
- **Configure manually** has you pick the tenant root table, its tenant ID column and an enforcement mode (**Strict** or **Warn**). You also mark the global tables, and for each scoped table you pick the column that holds the root's tenant ID.

The manual form declares one root, and it scopes a table only by a column on that table. Add a table that reaches the root through a join in `tenant-policy.md`, or with **Draft with AI**. A table that is neither scoped nor global stays unknown, and **Strict** rejects queries that read it.

Either way, you review the policy before **Save** writes `tenant-policy.md`. A saved policy shows its table coverage and an **Edit** button.

[Scope queries to a tenant](/guides/multi-tenancy/) walks through using it, and [Tenant policy format](/reference/tenant-policy/) lists the policy's fields and what the tenant check requires.

## RAG Index

<figure>

![The RAG Index view with chunk counts, the index details, and the Query Debugger showing retrieved chunks](../../assets/studio/rag-index.png)

<figcaption>The RAG Index view: chunk counts, Index Details and the Query Debugger.</figcaption>
</figure>

The RAG Index view builds the retrieval index and shows what retrieval returns for a question:

- **Build Index** chunks the artifact and embeds the chunks the store doesn't already hold, so a rebuild after a small change is quick. The cards count the chunks, how many are indexed, and the sensitive chunks left out or kept.
- **Index Details** shows the embedder the index was built with against the one your config names, the vector width, when it was built, and the store. **Stale** means the index no longer matches: the artifact's text changed since the last build, the embedder differs, or a build didn't finish. Build again.
- **Query Debugger** retrieves for a question, with a **Top K** (8 by default) and the chunk types to search. It lists each retrieved chunk with its score and text.

With `rag.embedder: "mock"`, which `askdb init` writes, Studio embeds with a local lexical embedder that needs no key. To embed with a model, see [RAG for large schemas](/guides/rag-for-large-schemas/).

## Playground

<figure>

![The Query Playground with a natural-language input field and a Generate SQL button](../../assets/studio/playground.png)

<figcaption>The Playground: type a question and generate SQL.</figcaption>
</figure>

The Playground is where you test whether your enrichment works:

<Steps>

1. Type a question in plain language.
2. Choose what the prompt holds, **Full schema** or **RAG**:
   - **Full schema** sends every tracked table with its columns, descriptions, aliases, enum values, column notes, foreign keys, common query language notes and business context, then your concepts. A sensitive table or column shows only names and types, with a sensitive tag ([Sensitive columns](/concepts/privacy-model/#sensitive-columns)). A table's example questions aren't part of it.
   - **RAG** retrieves only the relevant chunks, and is available once the index exists. It also shows each listed column's note and the business context it retrieves, under the same sensitive rules. See [What the model sees](/concepts/privacy-model/#what-the-model-sees).
3. If the schema has a tenant policy, the **Tenant scope** box is ticked. Set the access kind, the tenant root and IDs, and the SQL output, **$N parameters** or **Inline literals**. See [Scope queries to a tenant](/guides/multi-tenancy/#4-try-it-in-studios-playground).
4. Click **Generate SQL**, or press ⌘↵ (Ctrl+Enter).

</Steps>

The SQL appears with an **Explain** panel that shows the result of AskDB's SQL checks. Also there:

- **A sensitive-column warning.** When the SQL reads a column marked sensitive, a warning above it names the columns, as [`askdb ask`](/reference/cli/#output) prints it.
- **A `Note:` line.** It follows the warning when the check couldn't tell which tables the SQL reads.

Neither blocks the SQL. A query loaded from the history shows no warning: generate it again to see one. Like the CLI, the Playground follows `modes.omitSensitiveFromPrompt`.

The Playground doesn't show which chunks retrieval picked. To see them, run the same question in the [RAG Index](#rag-index) Query Debugger.

Some engines have no dialect that AskDB ships. For a schema on one of them, the Playground generates nothing and says so, as the CLI and the HTTP API refuse it. Set [`dialect`](/reference/config/#dialect) in `askdb.config.ts` to the built-in dialect your engine speaks.

Running the generated SQL against your database is off by default. [Enable Studio execute](/guides/enable-studio-execute/) turns it on.

### Get the code

Once the SQL looks right, the **Get the code** panel turns the session into TypeScript you can paste. The code holds your question, the schema path, the dialect, your AI provider and, when it's on, the tenant scope. Choose one of two styles:

- **Config-driven:** `createAskDb()` from `@askdb/client`, which reads the same `askdb.config.ts`.
- **Direct:** `ask()` from `@askdb/core`, with a model you pass.

Then continue with [Embed in a Node app](/guides/embed-in-node/). For a schema whose engine AskDB ships no dialect for, the panel shows why instead of code.

## Settings

<figure>

![The Settings view with the Workspace, RAG Store and Schema Warnings cards](../../assets/studio/settings.png)

<figcaption>Settings: the Workspace, RAG Store and Schema Warnings cards.</figcaption>
</figure>

Settings, at the bottom of the side rail, shows how Studio is set up. It changes nothing:

- **Workspace:** the schema ID and path, the AI provider (`ai.provider`) and model (`ai.language.model`, or the provider's default), and whether AI suggestions are configured.
- **RAG Store:** the embedder, the store, and whether the lock file and the store's files exist. The embedder comes from `rag.embedder`, with `ai.embedding` for `"ai"`. The store comes from `rag.store` and `rag.storeConfig`.
- **Schema Warnings:** the warnings from loading your schema artifact, such as a table with no markdown file. [Loader warnings](/reference/schema-artifact-format/#loader-warnings) explains each kind.

The rail's **Dark mode** button switches Studio's theme.
